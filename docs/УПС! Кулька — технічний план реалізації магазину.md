# УПС! Кулька — технічний план реалізації магазину

Nov 3, 2026 · @Volodymyr

## Коротко

Рекомендую **FastAPI + PostgreSQL** на бекенді і **Next.js (React) із серверним рендерингом** на фронтенді, усе в Docker на одному VPS з автоматичним деплоєм через GitHub Actions. Звичайний React без Next.js тут не підходить: він віддає порожню сторінку, яку заповнює JavaScript, а для десятків SEO-підбірок потрібні готові HTML-сторінки, які швидко відкриваються на телефоні і добре індексуються Google.

| Рішення | Вибір | Чому |
| --- | --- | --- |
| Підхід до розробки | Spec-driven: [GitHub Spec Kit](https://github.com/github/spec-kit) + OpenAPI як єдиний контракт | Доречно: проєкт середнього розміру, дві частини (бек/фронт), частину коду зручно писати з AI-агентом |
| Бекенд | Python 3.13, FastAPI, Pydantic v2, SQLAlchemy 2 (async), Alembic, PostgreSQL 17, Redis | Ваш вибір; модульний моноліт за чистою архітектурою; FastAPI сам генерує OpenAPI-схему |
| Фронтенд | [Next.js 16](https://nextjs.org/blog) (App Router, Server Components), TypeScript, Tailwind CSS | Готовий HTML для SEO, кеш сторінок, мінімум JavaScript на телефоні |
| Зображення | При завантаженні — конвертація в AVIF + WebP кількох розмірів (libvips: sharp або pyvips) | Візуально без втрат якості, у 5–10 разів легше за JPEG з телефона |
| Адмінка | Власна проста адмінка в Next.js (або SQLAdmin на старті) | Товари, підбірки, замовлення, фото з телефона |
| Інфраструктура | VPS (2 vCPU, 4 ГБ), Docker Compose, Caddy (HTTPS), GitHub Actions → GHCR → деплой по SSH | Дешево, просто, легко відкотити версію |

Оцінка обсягу — приблизно 8–10 тижнів роботи одного full-stack розробника до запуску версії, яка замінить нинішній сайт (дорожня карта нижче). Старий сайт працює до дня перемикання, замовлення не втрачаються.

## Архітектура

Усе працює на одному сервері в окремих Docker-контейнерах; покупець бачить лише Caddy, а база даних і Redis ззовні недоступні.

Сторінки Next.js запитують дані в FastAPI на сервері і кешують їх, тому більшість переглядів не доходить до бази. Важка робота (стиснення фото, сповіщення) йде в фоновий worker через чергу в Redis. Платіжний сервіс надсилає webhooks у FastAPI, бекапи їдуть на зовнішнє сховище.

## Spec-driven development

Spec-driven тут доречний, але на двох рівнях: **специфікації функцій** (що і навіщо робимо) і **контракт API** (як фронт говорить із беком). Перше дає порядок у вимогах і добре працює з AI-агентами, друге гарантує, що фронт і бек не розійдуться.

### Рівень 1 — специфікації функцій (Spec Kit)

[Spec Kit](https://github.com/github/spec-kit) — відкритий інструмент GitHub, що працює з Claude Code, Copilot, Gemini CLI та іншими агентами ([огляд](https://visualstudiomagazine.com/articles/2026/05/12/github-spec-kit-takes-off-as-antidote-to-piecemeal-vibe-coding.aspx)). Цикл для кожної функції:

1. **Constitution** (один раз на проєкт) — правила: «мобільний перший», «LCP < 2,5 с на 4G», «усі публічні сторінки рендеряться на сервері», «кожна зміна API спершу в OpenAPI», «тести обов’язкові», «українська мова інтерфейсу», «чиста архітектура: домен не залежить від фреймворків».
2. **Specify** — опис функції мовою бізнесу: хто, що робить, критерії приймання (наприклад «Покупець обирає дату і 2-годинний інтервал, зайняті інтервали недоступні»).
3. **Plan** — технічне рішення: модель даних, ендпоінти, компоненти.
4. **Tasks** — список дрібних задач з порядком.
5. **Implement** — код і тести (вручну або агентом), рев’ю людиною.

Специфікації лежать у репозиторії в `specs/NNN-назва/` і проходять рев’ю як код. Перші спеки: `001-catalog`, `002-collections-seo`, `003-product-page`, `004-cart-checkout`, `005-delivery-slots`, `006-payments`, `007-admin`, `008-notifications`, `009-media-pipeline`.

### Рівень 2 — контракт API (OpenAPI)

- **Джерело правди — Pydantic-моделі FastAPI.** FastAPI сам генерує `openapi.json`; його експортуємо у `contracts/openapi.json` і комітимо. Так немає двох описів, які треба синхронізувати вручну.
- **Фронт генерує клієнта** з цього файлу (openapi-typescript + openapi-fetch або Orval): типи TypeScript завжди збігаються з бекендом.
- **CI перевіряє дрейф:** якщо код змінив API, а `openapi.json` не оновлено, — збірка падає. Ламаючі зміни ловить oasdiff.
- **Контрактні тести:** Schemathesis ганяє API по схемі і шукає відповіді, що їй не відповідають.

Що свідомо не робимо: не пишемо спеку на кожну дрібницю (помилка в тексті, колір кнопки) — тільки на функції, де є логіка або дані.

## Каталог і SEO-підбірки

Головна ідея: товар не лежить в одній категорії, а має **теги з кількох вимірів**. **Підбірка** — це збережене правило з тегів плюс власна сторінка (URL, заголовок, текст, FAQ). Так один товар «Рожевий шик» сам потрапляє в «Для дівчинки», «Пастельні тони», «День народження» і «До 1500 грн», а нова підбірка створюється в адмінці за хвилину без програміста.

### Виміри тегів

| Вимір | Приклади значень | Приклад URL підбірки |
| --- | --- | --- |
| Привід | день народження, 1 рік, виписка, гендер-паті, випускний, 1 вересня, 14 лютого, 8 березня, день матері, Новий рік, Хелловін, весілля, освідчення | `/kulky/vypyska` |
| Для кого | дівчинка, хлопчик, дівчина, хлопець, мама, тато, колега, вчителька | `/kulky/dlia-divchynky` |

| Колір / стиль | пастельні, золото-чорні, рожеві, блакитні, райдужні, хром, мінімалізм | `/kulky/pastelni` |
| Тип | латексні, фольговані, цифри, фігури, фонтан, букет, бокс-сюрприз, фотозона, з написом | `/kulky/tsyfry` |

### Які комбінації індексувати

Якщо індексувати всі комбінації фільтрів, вийдуть тисячі сторінок з 2–3 товарами, і Google сприйме їх як сміття. Правило:

- **Індексуємо** лише підбірки, які створено в адмінці: вони мають унікальний заголовок, 150–300 слів тексту, FAQ, і в них не менше 6 товарів. Вони йдуть у sitemap.xml.
- **Не індексуємо** довільні фільтри, сортування і пошук (`?color=…&sort=…`): `noindex, follow` і canonical на батьківську підбірку.
- Кожна підбірка має одну канонічну адресу, навіть якщо її можна відкрити різними шляхами.
- Порожня або сезонна підбірка (Хелловін у липні) не видаляється: сторінка лишається, з блоком «замовте заздалегідь» і схожими товарами, щоб не втратити позиції до наступного сезону.

### Що на сторінці підбірки

1. Хлібні крихти і H1 («Гелієві кульки для дівчинки — Київ, Троєщина»).
2. Короткий вступ в 1–2 речення; довший текст — після товарів, щоб не заважати покупцю.
3. Чіпси суміжних підбірок («Пастельні», «1 рік», «Єдиноріг», «До 1000 грн») — сильна внутрішня перелінковка і швидка навігація.
4. Сітка товарів 2 в ряд, фільтри в нижній шторці.
5. SEO-текст, FAQ (розмітка FAQPage), відгуки з цієї підбірки.
6. Розмітка schema.org: BreadcrumbList, ItemList, Product/Offer на картках, LocalBusiness на сайті.

### Мобільна навігація

- Головна на телефоні починається з питання **«Яке свято?»** — великі плитки з фото: День народження, Виписка, Для неї, Для нього, Цифри, Найближче свято (міняється автоматично).
- Далі крок **«Для кого?»** (дівчинка / хлопчик / дорослий) і одразу сторінка підбірки: 2 тапи до товарів.
- Нижня панель: Каталог · Пошук · Кошик · Написати (Viber/Telegram).
- Пошук із підказками і синонімами («шарики» = «кульки», «єдиноріг» = «единорог», «днюха» = «день народження»), стійкий до одруків: на старті вистачить PostgreSQL (pg\_trgm + словник синонімів), без окремого пошукового сервера.
- Фільтри — у шторці знизу, кнопки не менше 44×44 px, лічильник «Показати 23 товари» на кнопці.

## Фронтенд, швидкість і зображення

Next.js рендерить публічні сторінки на сервері і кешує їх, тому телефон отримує готовий HTML за сотні мілісекунд; JavaScript вантажиться лише для інтерактивних частин (кошик, фільтри, оформлення).

### Сторінки

| Сторінка | URL | Як рендериться |
| --- | --- | --- |
| Головна | `/` | статично, оновлення при зміні в адмінці |
| Підбірка | `/kulky/[slug]`, `/kulky/[slug]/[sub]` | статично + інвалідація за тегом «collection» |
| Товар | `/tovar/[slug]` | статично + інвалідація за тегом «product» |
| Доставка за районом | `/dostavka-kulok/[district]` | статично |
| Кошик, оформлення, «Дякуємо» | `/koshyk`, `/oformlennia` | на клієнті, `noindex` |
| Доставка і оплата, Про нас, Контакти, FAQ, Блог ідей | `/dostavka`, `/pro-nas`, `/blog/[slug]` | статично |
| Адмінка | `/admin/*` | на клієнті, за логіном, `noindex` |

Коли в адмінці змінюють товар, бекенд викликає ендпоінт ревалідації Next.js, і зачеплені сторінки оновлюються за секунди. Ціна і наявність у кошику завжди перевіряються бекендом, а не беруться з кешу.

### Цілі швидкості (Core Web Vitals на телефоні)

| Метрика | Ціль |
| --- | --- |
| LCP (завантаження головного фото) | < 2,0 с |
| INP (відгук на тап) | < 200 мс |
| CLS (стрибки верстки) | < 0,05 |
| JavaScript на сторінці підбірки | < 150 КБ (gzip) |
| Вага першого екрана разом із фото | < 400 КБ |

Практики: системний або один варіабельний шрифт через `next/font` з кириличним сабсетом; перше фото з `priority`, решта ліниво; фіксовані пропорції карток (4:5), щоб не було стрибків; аналітика і піксель вантажаться після взаємодії або згоди на cookie; Lighthouse CI у пайплайні блокує реліз, якщо метрики погіршились.

### Зображення: стиснення без помітної втрати якості

Ви праві — такі бібліотеки є. Основа практично всіх сучасних рішень — **libvips**: у Node.js це **sharp** (його використовує сам Next.js), у Python — **pyvips**, а готовий сервер для фото на ній — **imgproxy**. Важливий нюанс: стиснення буквально «без втрат» (lossless) для фото дає мало — файл лише трохи менший. Реальний виграш дає **візуально безвтратне** стиснення в AVIF/WebP і зменшення до розміру екрана: фото з телефона на 3–5 МБ стає 40–120 КБ, і оком різниці не видно.

Рекомендований конвеєр (спека `009-media-pipeline`):

1. Адмін завантажує оригінал з телефона; він зберігається назавжди (на випадок нових форматів).
2. Фонова задача на бекенді (pyvips): поворот за EXIF, видалення метаданих і геолокації, колір у sRGB, обрізка 4:5.
3. Варіанти шириною 320, 480, 640, 960, 1280 px у **AVIF** (якість \~55–65) і **WebP** (\~80) плюс крихітний розмитий плейсхолдер. Точні числа підібрати на 10–20 ваших фото, порівнюючи оком і метрикою SSIMULACRA2.
4. Файли з хешем у назві віддає Caddy з `Cache-Control: immutable` на рік; згодом можна поставити Cloudflare або Bunny CDN.
5. На фронті `next/image` з власним loader, що бере готові розміри (`srcset` + `sizes`). Так VPS не стискає фото на кожний запит.

Альтернатива, якщо не хочете писати конвеєр: контейнер imgproxy, який стискає фото на льоту, а результат кешується в Caddy або CDN.

## Бекенд FastAPI

Один сервіс із чіткими модулями (модульний моноліт за чистою архітектурою), а не мікросервіси: для одного-декількох магазинів це простіше і дешевше, а модулі можна винести пізніше, якщо знадобиться.

### Стек

Python 3.13 · FastAPI · Pydantic v2 і pydantic-settings · SQLAlchemy 2 (async) + asyncpg · Alembic (міграції) · PostgreSQL 17 · Redis (кеш, черга, обмеження частоти запитів) · фонові задачі на arq або Dramatiq · uv (залежності) · Ruff (лінтер) · mypy/pyright · pytest + testcontainers (справжній PostgreSQL у тестах) · structlog + Sentry.

### Чиста архітектура

Кожен модуль будуємо за чистою архітектурою (порти і адаптери): бізнес-правила не залежать від FastAPI, SQLAlchemy чи платіжного сервісу. Залежності йдуть лише всередину: presentation → application → domain, а infrastructure реалізує інтерфейси, оголошені в application.

| Шар | Що там лежить | Приклад у модулі orders | Може імпортувати |
| --- | --- | --- | --- |
| domain | сутності, value objects, бізнес-правила, доменні події — чистий Python | `Order`, `Money`, `PhoneNumber`, `DeliverySlot`; правило «статус не можна повернути назад»; подія `OrderPlaced` | нічого зовнішнього |
| application | use cases (сценарії), інтерфейси-порти, DTO | `PlaceOrder`, `ConfirmPayment`; порти `OrderRepository`, `PaymentGateway`, `Notifier`, `UnitOfWork` | domain |
| infrastructure | реалізації портів | `SqlAlchemyOrderRepository`, `MonobankGateway`, `TelegramNotifier`, моделі таблиць SQLAlchemy | application, domain |
| presentation | HTTP: роутери FastAPI і Pydantic-схеми (саме вони дають OpenAPI) | `POST /orders` викликає `PlaceOrder` | application |

```text
backend/src/ups_kulka/
  modules/
    orders/
      domain/          # order.py, money.py, events.py
      application/     # place_order.py, ports.py, dto.py
      infrastructure/  # sqlalchemy_repo.py, tables.py
      presentation/    # router.py, schemas.py
    catalog/ ...  collections/ ...  payments/ ...
  shared/              # базові Entity, UnitOfWork, шина подій
  main.py              # збирає залежності (composition root)
```

Правила, щоб архітектура не розповзлась:

- **Межі перевіряє CI:** import-linter забороняє імпорти з infrastructure чи FastAPI у domain/application, а також прямі імпорти між модулями (лише через їхні публічні сервіси або доменні події).
- **Транзакції через Unit of Work:** use case відкриває UoW, репозиторії працюють у ньому, події публікуються після commit (outbox-таблиця, щоб сповіщення не втрачались).
- **Залежності впроваджуються** в одному місці (вбудований `Depends` FastAPI або бібліотека Dishka).
- **Тести за шарами:** domain і use cases — швидкі юніт-тести з фейковими репозиторіями без бази; infrastructure — інтеграційні з PostgreSQL; presentation — контрактні (Schemathesis).
- **Без фанатизму:** для простого читання (список товарів підбірки) дозволені окремі query-сервіси, які одразу повертають DTO (легкий CQRS). Повна доменна модель потрібна там, де є правила: замовлення, слоти, оплата, промокоди.

На фронтенді той самий принцип — у формі Feature-Sliced Design (`app / pages / widgets / features / entities / shared`): згенерований API-клієнт лежить у `shared/api`, і компоненти не звертаються до нього напряму мимо свого слайсу. Вимогу «чиста архітектура + перевірка меж у CI» варто записати в constitution Spec Kit.

### Важливі деталі

- **Слоти доставки:** кожен слот має ліміт замовлень (наприклад 4 за 2 години). Бронювання слота та створення замовлення — одна транзакція з блокуванням, щоб у пікові дні (14 лютого, 8 березня) не прийняти більше, ніж можете зібрати.
- **Ціна завжди рахується на сервері**, а не приймається з фронту. Гроші — цілі копійки (integer), а не float.
- **Оплата:** один інтерфейс і адаптери під українські платіжні сервіси (наприклад monobank еквайринг, LiqPay, WayForPay — вибір за вами). Webhooks з перевіркою підпису і ідемпотентністю: повторне сповіщення не створює другої оплати. Варто уточнити з бухгалтером питання фіскалізації (ПРРО).
- **Сповіщення:** нове замовлення миттєво приходить у Telegram-чат магазину з кнопками «Прийнято / Зібрано / Виїхала», які міняють статус у базі. Клієнт отримує підтвердження і після доставки — прохання про відгук.
- **Безпека:** обмеження частоти на формах, Cloudflare Turnstile від ботів, секрети лише в змінних середовища, персональні дані клієнтів — мінімум і лише зі згодою.
- **Міграція зі старого сайту:** скрипт переносить 60 товарів і фото, старий домен oops.kylka.shop робить 301-редирект на новий.

## Інфраструктура і CI/CD

Один VPS з Docker Compose вистачить і для кількох магазинів; Kubernetes тут зайвий. Код потрапляє на сервер лише як готові образи, зібрані та перевірені в CI, тому відкат — це запуск попереднього тегу.

### Репозиторій (монорепо)

```text
ups-kulka/
  .specify/            # Spec Kit: constitution, шаблони
  specs/               # 001-catalog, 002-collections-seo, ...
  contracts/openapi.json
  backend/             # FastAPI, Alembic, tests
  frontend/            # Next.js, згенерований API-клієнт
  deploy/              # compose.prod.yml, Caddyfile, скрипти бекапів
  .github/workflows/   # ci.yml, deploy.yml
```

### Контейнери на VPS

| Сервіс | Образ | Роль |
| --- | --- | --- |
| caddy | caddy | HTTPS (автоматичний Let’s Encrypt), HTTP/3, стиснення, роздача фото з довгим кешем, редирект зі старого домену |
| web | власний (Next.js standalone) | вітрина і адмінка |
| api | власний (FastAPI + Uvicorn) | API |
| worker | той самий образ, інша команда | фото, сповіщення, нагадування |
| db | postgres:17 | дані |
| redis | redis / valkey | кеш і черга |
| backup | приклад: restic або pgBackRest | щодня бекап бази і фото на зовнішнє сховище (S3-сумісне) |

Образи: багатостадійні Dockerfile, запуск від не-root користувача, healthcheck на кожному сервісі, база і Redis зовні недоступні.

### Пайплайн (GitHub Actions)

1. **Pull request:** Ruff, mypy, pytest (з PostgreSQL у контейнері); ESLint, TypeScript, Vitest; перевірка, що `openapi.json` актуальний, і oasdiff на ламаючі зміни; Schemathesis; Playwright e2e на головних сценаріях (підбірка → товар → кошик → замовлення); Lighthouse CI з порогами з розділу про швидкість.
2. **Merge в main:** збірка образів з кешем, сканування вразливостей (Trivy), публікація в GitHub Container Registry з тегом-комітом.
3. **Staging:** автоматичний деплой на staging (можна на тому ж VPS із субдоменом і `noindex`), smoke-тести.
4. **Production:** деплой за кнопкою (GitHub Environments із підтвердженням): SSH на VPS → `docker compose pull` → міграції Alembic окремим кроком → `docker compose up -d` → healthcheck → при збої автоматичний відкат на попередній тег.

Міграції пишемо сумісними зі старою версією коду (спочатку додати колонку, потім видалити стару наступним релізом), щоб відкат був безпечним.

### Надійність і моніторинг

- Бекапи: щодня, зберігати 30 днів, раз на місяць — пробне відновлення на staging. Бекап, який ніколи не відновлювали, не вважається бекапом.
- Помилки: Sentry (фронт і бек). Доступність: Uptime Kuma або Better Stack зі сповіщенням у Telegram.
- Сервер: SSH лише за ключем, фаєрвол (відкриті 22, 80, 443), автооновлення безпеки ОС, окремий користувач для деплою.
- Оновлення залежностей: Renovate або Dependabot. Next.js має регулярні щомісячні релізи безпеки ([блог](https://nextjs.org/blog)), їх варто ставити одразу.
