# 010 — План

- Дані: `backend/seed/old_site_catalog.json` (категорії → теги, товари).
- Транслітерація: `ups_kulka/shared/domain/transliteration.py`
  (`to_slug(text)`), unit-тести на прикладах з постанови.
- Скрипт: `backend/scripts/import_old_site.py`, бере use cases з DI-контейнера.
  Товари імпортуються за зростанням старого id, щоб нові були першими.
- Стара ціна: якщо на старому сайті вона більша за поточну, переноситься в
  `old_price_kopecks` (на вітрині — закреслена ціна й знижка).

## Фото товарів (через конвеєр 009-media)
- `plan_legacy_import` повертає ще й `photos`: пари `(slug, image_url)`.
- Use case `catalog.ImportLegacyPhotos` для кожної пари:
  1. бере товар за slug (активний чи ні); якщо фото вже є — пропускає
     (повторний запуск безпечний);
  2. завантажує файл через порт `PhotoDownloader`;
  3. передає байти в порт `PhotoUploader` → `media.application.public.MediaFacade.import_photo`
     (той самий конвеєр, що й в адмінці: поворот, обрізка 4:5, WebP 320–1280w);
  4. прив'язує фото до товару і зберігає.
  Помилка одного фото (немає файлу, замале, не картинка) не зупиняє імпорт:
  товар потрапляє у звіт `failed` з причиною.
- Адаптери: `HttpPhotoDownloader` (httpx, тайм-аут, ліміт 15 МБ, лише
  `image/*`), `MediaPhotoUploader` (фасад медіа).
- `MediaFacade.import_photo` — внутрішній виклик `UploadMedia` без перевірки
  токена: фасад не доступний через HTTP, ним користуються лише модулі й
  серверні скрипти.

## Запити
Імпорт — разовий; на товар 4–6 запитів для створення і ще 3–4 для фото
(товар за slug, медіа, збереження). Для 211 товарів це прийнятно; запитів у
вітрини це не змінює.

## Вітрина
Конвеєр обрізає фото до 4:5, тому картки й фото товару на вітрині теж 4:5
(`aspect-[4/5]`), щоб нічого не обрізалось удруге.
