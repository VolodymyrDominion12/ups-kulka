# 012 — Викладення на сервер (staging і production)

Статус: в роботі. Домен і VPS ще не обрані (питання з технічного плану).

## Навіщо
Магазин має працювати на власному домені з HTTPS, а кожна зміна в `main`
має потрапляти на сайт сама, з перевіркою і без простою; якщо нова версія
не стартувала — сайт лишається на попередній.

## Сценарії
1. Зміна злита в `main`, CI зелений → GitHub Actions збирає два образи
   (API і вітрина) один раз і викладає їх на staging, потім на production
   (production — після підтвердження в GitHub, якщо воно увімкнене).
2. Деплой: Caddy → завантаження образів → база → міграції → нові контейнери;
   чекаємо healthcheck. Якщо нова версія не піднялася — повертаємо попередню.
3. Відкат вручну: `deploy/deploy.sh production <старий-тег>` на сервері.
4. Щодня бекап бази, щотижня — архів фото; зберігаються 14 днів.
5. Старий домен `oops.kylka.shop` → 301 на новий (після перенесення його DNS).

## Критерії приймання
- Назовні відкриті лише 80/443 (Caddy); база недоступна ззовні.
- HTTPS-сертифікати Let's Encrypt оформлюються й оновлюються самі.
- Фото з `/media` віддає Caddy з диска з кешем на рік, без API.
- Staging закритий від пошуковиків (`X-Robots-Tag`, `robots.txt`).
- API на staging/production не стартує зі стандартним паролем адмінки
  або коротким ключем підпису.
- Один образ для staging і production: адреса сайту береться під час запуску.
- Після деплою smoke-тест ззовні: головна, каталог, API, robots, sitemap.
- Секрети — лише у файлах `env/*.env` на сервері та в GitHub Secrets.
