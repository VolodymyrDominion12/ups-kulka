# AGENTS.md — правила для всіх агентів і розробників

Цей файл обов'язковий до прочитання перед будь-якою зміною коду. Він діє для
Claude Code, Copilot, Cursor, Gemini CLI та людей. Деталі для бекенду —
у [`backend/AGENTS.md`](backend/AGENTS.md), архітектура — у
[`docs/architecture.md`](docs/architecture.md), незмінні принципи — у
[`.specify/memory/constitution.md`](.specify/memory/constitution.md).

Якщо правило заважає зробити задачу правильно — **не обходь його мовчки**:
зупинись, опиши конфлікт і запропонуй зміну правила (ADR у `docs/adr/`).

## 1. Проєкт

Інтернет-магазин повітряних кульок «УПС! Кулька» (Київ). Монорепо:

| Папка | Що там |
| --- | --- |
| `backend/` | FastAPI, чиста архітектура, PostgreSQL, Alembic |
| `frontend/` | Next.js (буде додано) |
| `contracts/openapi.json` | контракт API, генерується з бекенду |
| `specs/` | специфікації функцій (Spec Kit): `NNN-назва/spec.md, plan.md, tasks.md` |
| `docs/` | архітектура, ADR |
| `deploy/` | Docker Compose, Caddy, скрипти |

## 2. Як працювати над задачею (spec-driven)

1. Знайди або створи специфікацію в `specs/NNN-назва/`. Без спеки дозволені
   лише дрібні правки (опечатки, стилі, рефакторинг без зміни поведінки).
2. Онови `plan.md`: модель даних, use cases, ендпоінти, індекси, запити.
3. Пиши тести **до або разом** із кодом (див. розділ 4).
4. Реалізуй найменшими кроками; кожен крок — зелений `make check`.
5. Якщо змінився API — онови `contracts/openapi.json` (`make openapi`).
6. Перед завершенням пройди чек-лист у розділі 7.

## 3. Архітектурні правила (коротко; повністю — `backend/AGENTS.md`)

- **Роутер — тонкий.** Він лише: приймає HTTP-схему → викликає один use case →
  перетворює результат у HTTP-схему. Жодних `if` по бізнес-правилах, жодних
  запитів до БД, жодного `session`, жодних обчислень цін.
- **Бізнес-логіка — у use cases** (`application/use_cases/`) і в доменних
  об'єктах (`domain/`). Use case = один сценарій = один клас з методом
  `async def __call__(...)` (або `execute`).
- **Робота з БД — тільки через репозиторії** (`infrastructure/repositories/`),
  що реалізують порти (інтерфейси-`Protocol`) з `application/ports.py`.
- **Транзакції — через Unit of Work**, який відкриває use case.
- **Залежності — через DI-контейнер** (`dependency-injector`), зібраний в одному
  місці (`ups_kulka/container.py`). Нічого не створюй вручну в роутерах.
- **Напрям залежностей:** `presentation → application → domain`;
  `infrastructure → application, domain`. Домен не знає про FastAPI,
  SQLAlchemy, Pydantic, HTTP.
- **Модулі не лізуть один в одного.** Модуль `A` може імпортувати з модуля `B`
  лише `B.application.public` (публічний фасад). Таблиці іншого модуля напряму
  не читаємо.
- Ці правила **перевіряються автоматично** тестами в
  `backend/tests/architecture/`. Червоний архітектурний тест не можна
  «виправляти» додаванням винятку без ADR.

## 4. Тестування — обов'язкове

- Будь-яка зміна поведінки = новий або змінений тест. PR без тестів не приймається.
- **Unit** (`tests/unit/`): домен і use cases з фейковими репозиторіями, без БД,
  без мережі. Мають бути швидкими (< 1 с на файл).
- **Integration** (`tests/integration/`): репозиторії та API на справжньому
  PostgreSQL (testcontainers або `TEST_DATABASE_URL`). SQLite для тестів
  **заборонений** — він поводиться інакше.
- **Architecture** (`tests/architecture/`): правила залежностей і тонкі роутери.
- **Migrations** (`tests/migrations/`): міграції застосовуються з нуля,
  `alembic check` не бачить розбіжностей, усі зовнішні ключі мають індекс.
- Баг виправляється так: спершу тест, що його відтворює (червоний), потім фікс.
- Не вимикай, не пропускай (`skip`, `xfail`) і не послаблюй існуючі тести,
  щоб «пройшло». Якщо тест справді хибний — поясни чому в PR.
- Покриття для `domain/` і `application/` — не нижче 90 %.

## 5. База даних: індекси та запити

### Якщо змінилась схема даних (моделі, міграції)

- [ ] Є міграція Alembic, вона оборотна (`downgrade` працює) і сумісна зі
      старою версією коду (спершу додаємо, видаляємо — наступним релізом).
- [ ] **Кожен зовнішній ключ має індекс** (перевіряє тест
      `test_foreign_keys_are_indexed`).
- [ ] Кожна колонка, за якою фільтруємо, сортуємо або джойнимо в нових
      запитах, покрита індексом; для `WHERE a = ? ORDER BY b` — складений
      індекс `(a, b)`; для унікальних бізнес-ключів (`slug`, телефон) —
      `UNIQUE`.
- [ ] Немає зайвих індексів-дублікатів (індекс `(a)` при існуючому `(a, b)`).
- [ ] Для великих таблиць індекси створюються `CONCURRENTLY` в окремій міграції.
- [ ] У `plan.md` специфікації записано, які індекси додано і для яких запитів.

### Якщо додано або змінено запити до БД

- [ ] **Немає N+1.** Зв'язки завантажуються явно (`selectinload` / `joinedload`)
      або окремим пакетним запитом. За замовчуванням у моделях
      `lazy="raise"` — випадкове ліниве завантаження падає з помилкою.
- [ ] Є інтеграційний тест із `assert_max_queries(n)` (фікстура
      `query_counter`): кількість запитів **не росте** зі збільшенням кількості
      рядків (перевір на 1 і на 10+ записах).
- [ ] Для нових або змінених «важких» запитів (списки, пошук, звіти) виконано
      `EXPLAIN (ANALYZE, BUFFERS)` на реалістичних даних; у плані немає
      `Seq Scan` по великій таблиці там, де очікується індекс. Результат
      коротко описано в PR.
- [ ] Списки завжди з пагінацією (ліміт ≤ 100), без `SELECT *` у великих
      таблицях без потреби.
- [ ] Немає запитів у циклі (`for ... : await repo.get(...)`) — лише пакетні
      методи (`get_many(ids)`).

## 6. Стиль і інструменти

- Python 3.13, `uv` для залежностей, `ruff` (lint + format), `mypy --strict`
  для `domain/` і `application/`.
- Типи скрізь; `Any` — лише з коментарем чому.
- Гроші — `int` у копійках (`Money`), ніколи `float`.
- Час — `datetime` з часовою зоною (UTC у БД, `Europe/Kyiv` у відображенні).
- Секрети — лише зі змінних середовища; ніколи не комітити `.env`.
- Тексти для користувача — українською; код, коментарі, коміти — англійською.
- Коміти: Conventional Commits (`feat(catalog): ...`, `fix(orders): ...`).

## 7. Чек-лист перед завершенням задачі

- [ ] `make check` зелений (lint, типи, усі тести, архітектура, міграції).
- [ ] Роутери тонкі, бізнес-логіка в use cases / домені.
- [ ] Схема змінилась → індекси перевірено (розділ 5).
- [ ] Запити змінились → N+1 перевірено тестом, `EXPLAIN` для важких.
- [ ] API змінилось → `contracts/openapi.json` оновлено.
- [ ] Специфікацію (`specs/...`) оновлено, якщо поведінка відрізняється від плану.
- [ ] Немає закоментованого коду, `print`, TODO без номера задачі.

## 8. Команди

```bash
make install        # залежності
make up             # PostgreSQL і Redis у Docker для розробки
make migrate        # застосувати міграції
make run            # API на http://localhost:8000/docs
make test           # усі тести
make check          # lint + types + tests (те саме, що в CI)
make openapi        # оновити contracts/openapi.json
```
